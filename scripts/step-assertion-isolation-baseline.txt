# Workflow steps where ONE failing assertion silently skips the rest (bd-lagsa).
#
# THIS FILE IS NOW EMPTY OF ENTRIES, AND THAT IS THE POINT. Every step that was
# listed here has been converted to the accumulator idiom, so the gate accepts
# no exceptions: scripts/check-step-assertion-isolation.py fails on ANY step
# that runs two or more test-result assertions and aborts on the first failure.
#
# An entry may be added back only with a reason on the line above it. The gate
# still fails in BOTH directions, so an entry that starts accumulating again is
# itself an error telling you to delete the line -- this list cannot rot into an
# ignore-list.
#
# The idiom, as all fifteen safe steps now use it:
#
#     set -uo pipefail
#     failed=0
#     cargo test ... > "$log" 2>&1 || failed=1
#     grep -Eq 'test result: ok\. ...' "$log" || failed=1
#     ...
#     exit "$failed"
#
# `pipefail` is retained so a cargo failure upstream of a `tee` is still caught.
# Only `-e` is dropped.
#
# ---------------------------------------------------------------------------
# WHY THIS MATTERS, measured rather than argued, on 2026-10-05:
#
#   doctor-repair-receipts   a stale `7 passed` pin was grep 1 of 4. Correcting
#                            it resumed dispatch (28 tests), runtime (53) and
#                            cli (12) -- 93 TESTS that had not executed since
#                            2026-09-26, with nothing in the log saying they
#                            were missing.
#   primary-recovery         a stale `14 passed` pin was check 4 of 9, hiding
#                            three test groups, a jsonl recovery suite, and a
#                            `git diff --exit-code` working-tree guard.
#
# A brittle assertion is not merely noisy; in an aborting step it is a kill
# switch for everything downstream. An absent `test result:` line looks exactly
# like a test that was never going to run.
#
# THE EXIT CODE CANNOT TELL YOU WHICH HAPPENED. Simulated both forms of the
# session-arc step with the same planted failure: the aborting form died at unit
# 1 of 7 and the accumulating form ran all 7, and BOTH exited 1. That is the
# whole reason this gate reads structure instead of outcomes.
#
# promotion-recovery.yml is the counter-example that proves the idiom: it
# carried TWO stale counts, and because it accumulates BOTH suites still ran and
# both reported `0 failed`, which is how both wrong numbers were visible at once.
#
# ---------------------------------------------------------------------------
# NOT EVERY ABORTING STEP IS A DEFECT -- and this file used to claim otherwise.
#
# Five steps publish from INSIDE the asserting step: they run `git commit` and
# `git push origin HEAD:main` after their greps. There `set -e` is a PUBLICATION
# INTERLOCK. Converting one would run the push and only then exit 1, landing
# unverified code on main and reporting the failure afterwards -- strictly worse
# than a silent skip, because a stale pin in a publish-gating step is
# fail-CLOSED: nothing ships and the red is visible.
#
#   cass-prefetch-execution    cass-prefetch-residency    contradiction-graph
#   runtime-retrieval          session-arc "Publish tested source directly to main"
#
# The gate classifies these separately and never demands their conversion. They
# are NOT baselined, because they are not debt.
#
# The seven that were converted are safe to convert for a mechanical reason that
# was checked per step, not assumed: each either publishes in a LATER step whose
# `if:` is the default (doctor-index-repair, session-arc-learning), had already
# published upstream (index-recovery-admission), or never publishes at all. A
# converted step still exits 1, so the job fails and the later publish step is
# skipped. index-recovery-admission already ran the step-level form of this
# idiom -- `if: ${{ !cancelled() }}` on four consecutive verification steps.
#
# ORDERING TRAP, found by watching a predicate fail on real data. These lanes
# push inside a `for attempt in 1 2 3` retry loop and re-verify after merging
# origin/main, so assertions can sit textually AFTER the push they gate. A first
# pass asking "is there a side effect after the FIRST assertion?" classified
# session-arc's publish step as pure verification -- exactly the misreading that
# produces the unsafe conversion. The predicate is order-blind within a step,
# and the self-test carries that loop fixture plus a control with only the
# publish verbs stripped, which must still be flagged.
#
# ---------------------------------------------------------------------------
# MEASUREMENTS. The middle row is a correction, not progress:
#
#   at 2c7b5b9a5 (gate landed)      20 examined, 13 at risk,  7 safe, 18 at-risk assertions
#   doctor-repair-receipts fixed    20 examined, 12 at risk,  8 safe, 15 at-risk assertions
#   publish-gating separated        20 examined,  7 at risk, 12 counted, 8 at-risk assertions
#   all seven converted             20 examined,  0 at risk, 15 safe,  0 at-risk assertions
#                                   + 5 publish-gated, correct by design
#
# The textual assertion count UNDER-reports steps built on a helper. session-arc
# "Test explicit paired learning" shows 3 greps but executes 7 assertions, five
# of them through one `run_group` body; primary-recovery shows 2 and executes 9.
# The gate counts occurrences, so treat its number as a floor.
#
# NOT claimed: that any of these lanes passes. These conversions change failure
# PROPAGATION only -- no filter, pattern, count, log path or artifact
# expectation was touched. What they guarantee is that the next stale pin costs
# one red instead of silently switching off everything after it.
# ---------------------------------------------------------------------------

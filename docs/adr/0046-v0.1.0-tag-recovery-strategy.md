# ADR 0046: v0.1.0 Tag Recovery Strategy — Forward-Roll, Don't Re-Tag

Status: accepted
Date: 2026-05-27

## Context

The original `v0.1.0` git tag was pushed on 2026-05-15 at commit
`25700335e9387a3f041b11adf8672e9474487bce`. The corresponding GitHub
Release action ran `actions/checkout@v4` against that tag and failed
because `tests/audit_artifacts/latest_install_pipeline.json` was a broken
symlink in the tagged tree. The audit-artifact symlink was repaired in
the post-tag history but the tag itself still points at the broken-tree
commit, so:

- `git tag` shows `v0.1.0` exists locally and on `origin`.
- The `v0.1.0` GitHub Release page exists but carries **no asset
  binaries, no checksum manifest, no Sigstore bundle, and no provenance
  bundle**.
- The README install one-liner
  (`curl -fsSL https://github.com/Dicklesworthstone/eidetic_engine_cli/releases/latest/download/install.sh | bash`)
  redirects to the latest release with assets, which is `v0.3.1`
  (commit `ddf72b4d`, tagged 2026-05-26). The `v0.1.0` tag has not
  served the documented install path since the day it was created.
- bd-3usjw.72 was filed to prevent agents from "fixing" the missing
  release by moving the tag (`git tag -f`), force-pushing, or recreating
  the GitHub Release without an explicit decision record. The bead is
  operator-decision-gated by design.

Between the broken `v0.1.0` tag and today, the project has tagged and
released:

| Tag | Commit | Date | GitHub Release |
| --- | --- | --- | --- |
| v0.1.0 | `25700335` | 2026-05-15 | exists, **no assets** |
| v0.2.0 | `52a84df0` | 2026-05-21 | exists, with assets |
| v0.3.0 | `e89d008d` | 2026-05-25 | exists, with assets |
| v0.3.1 | `ddf72b4d` | 2026-05-26 | exists, with assets |

Each post-`v0.1.0` tag was cut at a tree where the audit-artifact
symlink had already been repaired, so the release workflow ran cleanly
and the install path returned 200.

The decision required by bd-3usjw.72 is therefore not "how do we cut
v0.1.0 again" but "what do we do with the historical tag that never had
assets, given that v0.2.0+ have already replaced it for the install
path?"

## Decision

**Adopt a forward-roll strategy:** treat the existing `v0.1.0` git tag
as immutable historical evidence of the broken-tree state on
2026-05-15, do not re-tag or force-push it, do not retroactively attach
assets to the GitHub Release, and treat `v0.2.0` as the first signed
release whose assets the install path depended on.

Concretely:

1. **`v0.1.0` git tag stays exactly where it is** (`25700335`). No
   `git tag -f v0.1.0`. No `git push --force origin v0.1.0`. No
   `git tag -d v0.1.0 && git tag v0.1.0 <new-commit> && git push
   origin v0.1.0`. The tag is part of the audit trail; the absence of
   assets on the corresponding GitHub Release is itself the record
   that the original release workflow failed.
2. **`v0.1.0` GitHub Release stays asset-free.** Do not retroactively
   upload binaries, checksums, Sigstore bundles, or provenance
   bundles to the historical release page. Doing so would create
   assets whose checksum manifests cannot be verified against
   anything the broken-tree release workflow produced — i.e. it would
   manufacture audit evidence for a release that did not actually
   happen.
3. **`v0.2.0` is the de-facto first signed release.** The
   `cargo install` story remains gated on the upstream path-dep
   publishing chain (bd-3usjw.11, bd-3usjw.11.1.*), but the
   `curl | bash` install path already works against the
   `releases/latest` redirect and resolves to `v0.3.1` today.
4. **bd-3usjw.9 (first_signed_release) closes on `v0.2.0`'s evidence**
   once the README install URL is confirmed to return 200 against the
   `latest` redirect. The README "Latest tag" row should be refreshed
   to cite `v0.3.1` (or whatever `latest` resolves to at close time)
   and the "GitHub Releases" row should flip from "No published
   release assets yet" to the actual asset state.
5. **README "Latest tag" + "GitHub Releases" rows must not mention
   `v0.1.0` as the current state of the project.** They are
   historical-snapshot rows and the snapshot is now `v0.3.1` or
   later.

## Consequences

What becomes easier:

- Agents stop trying to "fix" v0.1.0 by moving the tag, which would
  rewrite a public git tag pointer and break any consumer pinned to
  `25700335`.
- The audit trail stays honest: the `v0.1.0` release page being
  asset-free is the visible record of the broken-tree-symlink incident.
  Future release-workflow regressions can be diagnosed by comparing
  against that incident.
- bd-3usjw.9 can be closed against `v0.2.0`+ evidence without
  re-running anything against the `25700335` tree.
- bd-3usjw.72 has a recorded decision and closes against this ADR.

What becomes harder / intentionally impossible:

- There is no `0.1.0` package on crates.io that anyone can `cargo
  install ee --version 0.1.0` against. This is by design until the
  upstream path-dep publishing chain (bd-3usjw.11.1.*) completes;
  consumers must use the `curl | bash` install or build from source.
- `cargo install ee@^0.1` would resolve to a nonexistent version
  unless and until the crates.io publish chain catches up to a
  version >= 0.2.0. The crates.io row in the README current-state
  table already documents this with `publish = false` historical
  context.
- `releases/v0.1.0/download/install.sh` returns 404 on the asset URL
  forever. Any historical doc that copy-pasted that exact URL must
  be updated to `latest/` or to a specific newer tag.

## Rejected Alternatives

### A. Move the `v0.1.0` tag to a current commit

Rejected. `git tag -f` and force-push rewrite the meaning of a
versioned public reference. Any external consumer (a doc, a bookmark,
a downstream agent harness, a CHANGELOG entry, a SBOM) that pinned
`25700335` now points at a different tree under the same name. The
audit trail is destroyed.

### B. Delete the `v0.1.0` tag entirely

Rejected for the same reason as A, plus the additional concern that
a deleted-then-recreated tag is a strictly stronger form of audit-trail
rewriting. `git push origin :refs/tags/v0.1.0` is an irreversible
operation against the remote.

### C. Retroactively upload v0.3.1 assets to the v0.1.0 GitHub Release

Rejected. The asset checksum manifest in any release artifact bundle
records the *tree* the assets were built from. v0.3.1 assets built
from commit `ddf72b4d` cannot honestly claim to be `v0.1.0` assets
built from `25700335`. Uploading them under the v0.1.0 release name
would create a release whose installer reports a tag mismatch in
verbose mode and whose Sigstore bundle cert binding doesn't match the
release URL — a confusing audit-evidence collision.

### D. Cut a `v0.1.1` patch-fix at the post-symlink-repair commit and
attach all assets there

Rejected as redundant. `v0.2.0` already exists at `52a84df0` (also
post-symlink-repair) with full asset bundles. A `v0.1.1` cut after
`v0.2.0` would be a non-monotonic version bump (lower than v0.2.0)
that defeats semver expectations and confuses every dependency
resolver that has already pulled `v0.2.0`+ metadata.

### E. Reset main to before v0.1.0 was tagged

Rejected immediately. Per AGENTS.md "Irreversible Git & Filesystem
Actions" section, `git reset --hard` and tag rewriting are forbidden
without explicit operator authorization naming the exact commands and
consequences. Even if authorized, this would discard ~100 days of
post-v0.1.0 history.

## Verification

How tests, diagnostics, or review prove the decision remains true:

- `git tag --list v0.1.0` continues to resolve to `25700335` after
  this ADR lands. Any future commit that moves this tag is a
  contract violation against this ADR.
- The `v0.1.0` GitHub Release page continues to show "no assets" or
  equivalent. A release-workflow PR that uploads assets to v0.1.0 is
  a contract violation against this ADR.
- The README current-state table cites `v0.3.1` (or later) as
  "Latest tag" after the first README refresh that lands alongside
  closing bd-3usjw.9. The audit-install-pipeline gate
  (`scripts/audit_install_pipeline.sh` per the bd-3usjw.9 bead body)
  reports the live `latest` resolution rather than asserting `v0.1.0`.
- The closing comment on bd-3usjw.72 cites this ADR by number, and
  the closing comment on bd-3usjw.9 cites this ADR plus the live
  `latest` redirect evidence.
- Future agents that read bd-3usjw.72 and bd-3usjw.9 find this ADR
  via the bead comments and do not refile the same "should we fix
  v0.1.0?" question.
